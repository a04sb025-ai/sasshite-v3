## 1. 今回の目的

本編全体を作ることが目的ではありません。

エレベーターステージ1つだけで、プレイヤーが

**観察 → 判断 → 介入 / 非介入 → NPCの反応 → 再判断**

を自然に行い、その判断の揺れ自体がゲームとして面白いか検証できるPoCを作ってください。

正解当てゲームにはしないでください。

---

## 2. 正式画面基準

正式画面構図のSource of Truthは以下です。

`docs/art/references/stages/elevator/elevator-stage-v1-approved.png`

この画像の正式ファイル名は:

`elevator-stage-v1-approved.png`

です。

### 重要

この画像がリポジトリ内にまだ存在しない場合、Codexが似た画像・SVG・CSS人物を勝手に生成して代替してはいけません。

その場合は、

- 画像が不足していることを明示
- 非アート部分の実装だけ進められるか判断
- 正式画像の配置待ち部分を明確に分離

してください。

構図を独自に描き直して作業を完了したことにしないでください。

---

## 3. 画面構図で維持するもの

スマートフォン縦画面を最優先にしてください。

画面には同時に以下が読める必要があります。

1. エレベーターの開口部
2. 廊下
3. 外側NPC
4. ひかえめくん
5. 内側NPC
6. 実物風の開ボタン
7. 実物風の閉ボタン
8. 左右の扉

正式画像のカメラ位置・人物配置・静かな空気感を基本にしてください。

タイマー、正解表示、進路矢印、思考吹き出し、大きな3択UIは追加しないでください。

---

## 4. 画面を1枚画像として固定しない

正式画像は構図基準であり、完成画面を1枚のスプライトとして貼るための素材ではありません。

最低限、以下の責務を分離してください。

```text
ElevatorStage
├─ background / hallway
├─ doorLeft
├─ doorRight
├─ controlPanel
│  ├─ openButton
│  └─ closeButton
├─ player
├─ insideNpc
└─ outsideNpc
```

扉とNPCは動く必要があります。

背景の最終アート素材が未準備の場合、開発中だけ明確なプレースホルダーを使用して構いません。ただし、正式人物の代替イラストをSVG/CSSで描かないでください。

---

## 5. 扉の基本状態

扉は最低限、以下の状態を持たせてください。

```ts
type DoorState =
  | 'open'
  | 'open_wait'
  | 'closing'
  | 'opening'
  | 'closed';
```

実装上より適切な状態名へ変更して構いませんが、挙動は仕様に従ってください。

### 初期

- ステージ開始時は扉が完全に開いている。
- すぐには閉まらない。
- 通常のエレベーターのように、自然な開放待機時間を持つ。

初期値の目安:

- 自然開放待機: 1.5〜2.5秒

正確な値は定数化し、後から調整可能にしてください。

### 自然閉鎖

何も操作しなければ、開放待機後に扉がゆっくり閉まり始めます。

「何もしない」は正式なプレイヤー判断として成立します。

---

## 6. 開ボタン

実際の操作盤上の「開」ボタンをタップ / 押下可能にしてください。

見た目より少し広い透明ヒット領域を持たせて構いません。

挙動:

- 扉が `open` / `open_wait` の場合: 開状態を維持する
- `closing` の場合: 閉鎖を止め、再度開く
- `opening` の場合: 開動作を継続する
- 完全閉鎖前であれば、基本的に判断を修正できる

長押しを採用する場合でも、タッチ操作が不自然にならないことを優先してください。

---

## 7. 閉ボタン

実際の操作盤上の「閉」ボタンを操作可能にしてください。

重要:

**閉ボタンを押しても瞬間的に完全閉鎖しないでください。**

押した時点で、自然待機を打ち切って `closing` へ移行します。

閉まり始めてから完全に閉じるまでには、プレイヤーが「やっぱり開ける」と判断を修正できる猶予を持たせてください。

目安:

- 閉まり始め〜完全閉鎖: 1.0〜1.5秒程度

数値は調整可能な定数にしてください。

---

## 8. 閉まり途中の判断修正

このステージの重要なゲーム性です。

例:

1. プレイヤーが閉ボタンを押す
2. 扉が閉まり始める
3. 外側NPCがエレベーターを見る / 少し急ぐ
4. プレイヤーがそれに気づく
5. 開ボタンを押す
6. 扉が再び開く

この一連の操作を自然に成立させてください。

「一度閉ボタンを押したら失敗確定」にはしないでください。

---

## 9. 外側NPC

外側NPCは正解判定装置ではありません。

プレイヤーが

- このまま乗るのか
- 別方向へ行くのか

を観察する対象です。

### 初期位置

正式画面基準に従ってください。

スマホで、少なくとも

- 顔の向き
- 身体の向き
- 歩行方向

が読めるサイズを維持してください。

### 行動バリエーション

PoCでは最低限2パターンあると望ましいです。

#### A. 本当に乗る

- エレベーターへ向かう
- 途中で視線や速度が変化してよい
- 扉が閉まりかけると、弱い反応を見せる

#### B. 乗らず別方向へ行く

- 最初から答えを明示しない
- 曲がる前に予兆を出す
- いきなりランダムに90度曲がらない

予兆の順序は `elevator-observation-signals-v1.md` を参照してください。

例:

1. 視線が少し横へ向く
2. 顔が横へ向く
3. 上半身が少し横へ向く
4. 歩行ラインがずれる
5. 実際に進路を変える

プレイヤーによって、どの段階で「乗らない」と判断するかが変わることを狙います。

---

## 10. 内側NPC

内側NPCはプレイヤーへ答えを教えません。

待ち時間などに応じて、弱い反応を段階的に出してください。

例:

- 扉を見る
- 廊下を見る
- 小さく体重移動する
- ひかえめくんを見る
- ごく小さく息をつく

怒り顔、腕組み、時計連打などの露骨な「早くしろ」表現は避けてください。

プレイヤーが勝手にプレッシャーを感じる余地を残してください。

---

## 11. ひかえめくん

正式仕様:

- `docs/character-spec-player.md`
- `docs/art/references/player/02-character-reference-approved.png`

を優先してください。

Codexが人物を即興SVG/CSSで描き直すことは禁止します。

Riveアセットが未完成の場合は、キャラクター描画層をadapter化し、正式アセット待ちにしてください。

仮人物を「完成版」としてコミットしないでください。

---

## 12. ゲーム中に表示しないもの

以下は本番PoC画面へ表示しないでください。

- 制限時間
- カウントダウン
- 「早く！」等の指示
- NPCの気持ちのテキスト
- 正解 / 不正解
- スコア
- 好感度
- 感情ゲージ
- 進路矢印
- 「様子を見る」ボタン
- 行動タイプ診断

プレイヤーのフィードバックは人物と世界の反応で返してください。

---

## 13. 非介入

プレイヤーが何もボタンを押さない場合も、正常なプレイとして扱ってください。

- 扉は自然待機後に閉まり始める
- NPCは世界の時間に従って行動する
- 「操作してください」警告を出さない
- 無操作をエラー扱いしない

PoCではバックエンドへ個人データを保存しません。

---

## 14. 開発用イベントログ

将来の行動分析を考慮し、ゲームロジック内部ではイベントを構造化しておくと望ましいです。

ただしPoCでは**永続保存・送信しない**でください。

例:

```ts
type ElevatorStageEvent =
  | { type: 'stage_started'; atMs: number }
  | { type: 'open_pressed'; atMs: number; doorProgress: number }
  | { type: 'close_pressed'; atMs: number; doorProgress: number }
  | { type: 'door_closing_started'; atMs: number }
  | { type: 'door_reopened'; atMs: number }
  | { type: 'outside_npc_gaze_shift'; atMs: number }
  | { type: 'outside_npc_body_turn'; atMs: number }
  | { type: 'outside_npc_route_changed'; atMs: number }
  | { type: 'inside_npc_reaction'; atMs: number; level: number }
  | { type: 'door_closed'; atMs: number };
```

必要なら開発モードのみconsoleで確認できるようにしてください。

本番画面へ表示しないでください。

## 15. 状態管理

ゲームロジックと描画を密結合させないでください。

例:

```text
src/
├─ game/
│  └─ elevator/
│     ├─ ElevatorStageController.ts
│     ├─ ElevatorStageState.ts
│     ├─ DoorController.ts
│     ├─ OutsideNpcController.ts
│     └─ ElevatorStageEvents.ts
├─ rendering/
│  ├─ pixi/
│  └─ rive/
└─ main.ts
```

既存構成がある場合はそちらに合わせてよいですが、

- 扉ロジック
- NPC意思 / 演技
- PixiJS描画
- Rive接続

を可能な範囲で分離してください。

## 16. 最低限のテスト

少なくとも以下をテストしてください。

1. 開放待機後に自然閉鎖へ進む
2. 閉ボタンで自然待機を打ち切って閉まり始める
3. 閉まり途中の開ボタンで再度開く
4. 完全閉鎖前なら判断修正できる
5. 無操作でも正常にステージが進む
6. NPCルートBで、予兆イベントより前にルート変更イベントが発生しない
7. イベント時刻が単調増加する
8. ステージリセットで初期状態へ戻る

可能ならブラウザ上で開・閉のタッチ操作を確認するsmoke testも追加してください。

## 17. Androidスマホ最優先

- portraitで成立すること
- 実物風のボタンが小さくても、タッチ判定は十分確保すること
- ページスクロールと操作が競合しないこと
- NPCの顔・身体向きが小画面で読めること
- 扉アニメーションが滑らかであること
- 60fpsを目標とすること

外側NPCの仕草がスマホで読めない場合、アートを勝手に変える前に問題として報告してください。

## 19. 実装手順

1. 仕様をすべて読む
2. 現在のリポジトリ状態を確認
3. 正式画面画像と必要アセットの有無を確認
4. 不足アセットを明示
5. 状態設計を決める
6. 扉ロジックを実装
7. 開閉操作を実装
8. NPC行動ロジックを実装
9. 描画adapterを接続
10. typecheck
11. lint
12. test
13. build
14. 可能ならブラウザ確認
15. 変更内容と残課題を報告

チェックしていない項目を「成功」と書かないでください。

## 21. PoC合格判定

コードが動くだけでは合格ではありません。

人間がスマホで遊び、最低限以下を判断します。

1. 初見でエレベーターの状況が分かる
2. 外側NPCを見る必要がある
3. 内側NPCも自然に視界へ入る
4. 「開ける / 閉める / 何もしない」で少し迷う
5. 閉めかけて開け直す判断が自然にできる
6. NPCの反応を見て判断を変えたくなる
7. 正解表示がなくても場面の結果が理解できる
8. 操作がスマホで気持ちいい

ここでゲーム性が確認できるまで、ステージ量産へ進まないでください。
