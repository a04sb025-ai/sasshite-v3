## 1. この画像の役割

この画像は、エレベーターステージ「もう一人、来る？」の**本番ゲーム画面構図の正式基準**である。

基準にするもの:

- エレベーター内部から廊下を見るカメラ位置
- 開いた扉を中央に置く構図
- ひかえめくん、内側NPC、外側NPCの画面上の関係
- 操作盤の位置と見え方
- 廊下の奥行き
- 静かで柔らかい照明と空気感
- 情報を詰め込みすぎない画面密度
- 「待つ / 閉める / 何もしない」で迷える余白

この画像は、ゲーム中の最終レンダリングを1枚絵として固定するための素材ではない。

## 3. 絶対に維持する画面要素

1. スマートフォン縦画面を基準とする。
2. カメラはエレベーター内奥側から廊下方向を見る。
3. 開口部を画面中央の主な視線抜けにする。
4. ひかえめくんは操作盤側に置く。
5. 内側NPCは反対側手前に置き、外NPCを見る視野内に自然に入るようにする。
6. 外側NPCは廊下の中距離に置き、スマホでも身体・顔向きの変化が読める大きさを確保する。
7. 外側NPCが直進する可能性と、横方向へ進路を変える可能性の両方を成立させる。
8. 開・閉ボタンは実在のエレベーター操作盤の一部として見せる。
9. 開・閉ボタンに正解を示す色分けをしない。
10. 静かで柔らかい、少し気を遣う空気感を維持する。

## 4. 本番画面に追加しないもの（v1基準）

> **3ボタン版PoCの例外（2026-08-20）:** 新しい正式採用候補の検証では、下部に「開ける / 閉める / 様子を見る」を同格の明示ボタンとして配置する。以下の「大きな選択肢UIを追加しない」「何もしない専用ボタンを置かない」というv1方針より、この検証指示を優先する。実装分解と暫定素材は `../../../../poc/elevator-stage-three-button-assets.md` を参照する。

以下は追加しない。

- カウントダウンタイマー
- 制限時間ゲージ
- ヒントアイコン
- 進路を示す矢印
- NPCの思考吹き出し
- 「開ける / 閉める / 様子を見る」の大きな選択肢UI
- 「正解」「不正解」「SUCCESS」
- 感情ゲージ
- 「この人は乗ります」などの説明
- プレイヤーの判断を誘導する攻略文

「何もしない」は専用の大きなボタンにせず、**何も操作しないこと自体**で成立させる。

## 5. 実装時のレイヤー分解

正式画像をそのまま1枚の背景として固定しない。

最低限、以下を別責務として扱う。

```text
stage
├─ elevator_background
├─ hallway_background
├─ door_left
├─ door_right
├─ control_panel
│  ├─ open_button_hit_area
│  └─ close_button_hit_area
├─ player_hikaemekun
├─ inside_npc
└─ outside_npc
```

必要に応じて前景手すり、影、照明演出などを分離してよい。

### 扉

左右独立パーツとして動かす。

### キャラクター

最終人物をCodexが即興SVG/CSSで描き直してはならない。正式アート / Rive素材を使用する。

### 操作盤

見た目上のボタンよりタッチ判定領域を少し広くしてよい。ただし見た目を巨大なゲームUIへ変更しない。

## 6. 外側NPCの位置について

採用画像の位置・大きさをv1の基準とする。

目的は、開始時点で答えを断定させることではない。

外側NPCは、

- このままエレベーターへ来るかもしれない
- 途中で別方向へ行くかもしれない

という曖昧さを持つ。

ただし、単なるランダムな進路変更は禁止する。進路を変える場合は `elevator-observation-signals-v1.md` に従い、視線・顔・上半身・歩行ラインなどの予兆を順に見せる。

---

## 7. 内側NPCの役割

内側NPCは「早く閉めて」とプレイヤーへ指示する人物ではない。

- 扉を見る
- 廊下を見る
- 体重を少し移動する
- ひかえめくんを見る

など、複数解釈できる弱い反応だけを基本とする。

プレイヤーがその反応をプレッシャーと感じるかどうかも、ゲーム体験の一部である。

---

## 8. 変更ルール

この画像は **エレベーターステージ v1 の正式基準**として固定する。

今後、画像生成だけを理由に細部を変更し続けない。

変更するのは原則として以下の場合のみ。

- スマホ実機で重要なNPCの仕草が読めない
- 初見テストで構図が理解されない
- ほぼ全員が同じ判断を即決し、ゲームとして迷いが成立しない
- 実装上どうしても成立しない物理的矛盾が判明した

変更する場合は、先に仕様変更をdocsへ記録してから基準画像を更新する。
